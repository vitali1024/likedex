# Phase 4 YouTube Liked Videos provider ingestion

This implements ingestion against the committed specifications and Phase 3 bootstrap/request foundation. It creates in-memory domain records and provider evidence only. Synchronization, repository application, owner binding, finalization/pruning, durable attempt state, runtime routing and product UI remain later work. There is no automatic invocation from extension entrypoints. Maker verification is not independent review or live-account evidence.

## Requests and authentication boundary

`YouTubeLikedVideosProvider` receives the existing `GoogleAuthorizationRequests` boundary. Its `enumerateLikedVideos(context, signal)` async generator consumes the Phase 3 validated `{ channelId, channelTitle?, likesPlaylistId }` plus attempt UUID, generation and auth epoch. It never guesses or rediscovers the Likes playlist during ordinary enumeration.

The exact normal requests are:

```text
GET https://www.googleapis.com/youtube/v3/playlistItems?part=id%2Csnippet%2CcontentDetails%2Cstatus&maxResults=50&playlistId=<validated Likes ID>[&pageToken=<opaque token>]
GET https://www.googleapis.com/youtube/v3/videos?part=snippet%2CcontentDetails%2Cstatus&id=<comma-separated unique page IDs>
```

URLSearchParams encodes all values. The second call has at most 50 distinct video IDs, no `maxResults` or `pageToken`, and is skipped for empty membership. Each nonempty membership page normally makes one hydration call, including pages containing only previously observed videos; no cross-page metadata cache exists. Both use the ephemeral bearer header, reject redirects, omit ambient cookies and disable fetch caching. Endpoints/parts are fixed; no caller-supplied destination or write method exists. Permissions, manifest, Store identity and OAuth configuration are unchanged.

The Phase 3 token acquisition/cache invalidation code and HTTP/body deadline are shared. Each request acquires silently through Chrome's token cache; no token is saved in a class field, database, result or log. The first 401 in the ingestion session evicts that exact token, acquires one replacement silently, validates `channels.list` with the replacement, requires both original channel and Likes playlist IDs to match, then retries the original request. Another 401 invalidates the failing token and stops. No provider path opens consent. An owner recheck is justified only on recovery here; Phase 5 still owns initial/final owner validation and durable fences.

## Streaming and completion evidence

The generator yields `ProviderPage` events with domain records and cumulative pages/raw items/unique video membership/duplicate-video items/nullable estimated total. It fetches no later page until the consumer requests the next event. A page is prospective safe progress, never proof of full enumeration. Hydration must validate before that page is yielded; failure can leave earlier yielded pages but does not yield the failing page.

Only after the terminal page has been yielded and the stream has resumed with valid cancellation/time gates does it yield `TrustedProviderCompletion`. This has a private TypeScript brand and an in-process WeakSet provenance check (`isTrustedProviderCompletion`). It binds owner, Likes playlist, attempt UUID, generation/auth epoch, validator revision 1, validated page-chain summaries, actual raw/unique counts, complete video-ID set and terminal membership observation time. The object, nested evidence, scope and arrays are frozen; caller edits to earlier pages cannot rewrite it. A fabricated boolean, object spread, or JSON-deserialized summary cannot pass provenance validation.

This is **provider evidence**, not the full Phase 5 destructive domain capability. Phase 5 must consume pages sequentially, verify every safe transaction, revalidate owner, recheck active attempt/generation/auth epoch/eligibility, and atomically finalize before permitting removal. Serialized evidence is audit data only. Returning early, cancellation, invalid/untrusted input, hydration/transport failure or exhausted bounds produces no terminal capability. Errors remain errors; ingestion does not synthesize a successful empty/idle/partial sync state.

Only one validated first-to-terminal token chain can complete. Continuation follows the exact opaque token, regardless of page length. Empty-string/non-string tokens fail validation; a previously returned/requested token, cyclic chain, duplicate playlist-item ID or empty page with continuation fails closed. No arbitrary page cap or resume cursor exists. The 10-minute session budget bounds otherwise progressing chains.

`pageInfo` and nonnegative integer `resultsPerPage` are required; the latter must equal the actual page length, at most 50. Optional `totalResults` remains null until known. All present totals must agree across pages; cumulative raw items cannot exceed the total and terminal raw count must match it. Raw count includes distinct playlist-item IDs that refer to the same video. Missing totals on nonempty scans are allowed; totals alone never establish completeness. **Trusted empty requires an explicit valid first terminal `items=[]`, `resultsPerPage=0`, `totalResults=0`.** Missing items, missing pageInfo, absent zero-total evidence, error envelopes, malformed JSON or HTTP failures cannot become that control case.

## Runtime validation and mapping

Zod validates correct envelope/resource kinds, explicitly present item arrays, required snippet/contentDetails/status containers, nonempty identifier characters, 11-character video IDs, requested playlist identity and video-resource kind. At least one contentDetails/snippet membership video ID must be trustworthy; both must agree when supplied. An invalid/unmappable item invalidates trust for the scan rather than being skipped. Extra unrelated provider fields are discarded; an error envelope is explicitly rejected even if accompanied by success fields.

`videos.list` items must belong to the requested set and have unique IDs; they join membership by ID, regardless of response ordering. Unexpected IDs, duplicate metadata IDs, invalid containers/types/statuses/URLs or malformed metadata JSON fail the scan. A valid response may omit requested video IDs. That preserves membership with nullable rich fields and `unknown / lookup-omitted` availability, and does not invalidate enumeration completeness. Omission does not prove deletion or that the video was unliked.

Mapped results pass the existing `MirroredVideo` domain schema. They contain owner/attempt IDs, all observed membership source IDs, nullable metadata, availability evidence and actual per-fact observation/retention deadlines. No raw YouTube JSON reaches the eventual sync layer. Null metadata with null freshness is unknown/unrefreshed: Phase 5 must retain any eligible previously validated value with its original provenance rather than overwrite it or renew its deadline. Known mapped fields carry only their own hydration observation; `metadataFetchedAt` is the latest actual field observation, or null when nothing representable was observed. Lookup omission records availability observation, without renewing title/date/duration fields.

Distinct playlist-item IDs for one video are explicit duplicate-video membership. Each page emits one record per unique video; subsequent pages may emit an update with cumulative source IDs. Raw counts, unique counts and duplicate counts remain distinct. The first validated occurrence in the page chain supplies the canonical liked date and conservative membership observation time; later conflicting dates/positions do not silently replace it. Duplicate playlist-item IDs, whether identical or conflicting and whether within/across pages, prevent trusted completion. Hydration ordering and video publication dates never establish membership order. Pages preserve first-occurrence traversal order; the product specifies date-based local sorts and has no durable playlist-position sort.

`likedAt` comes only from playlist-item `snippet.publishedAt`, the documented addition time. The video's `snippet.publishedAt` independently supplies publication time; playlist-owner channel fields are never used as the creator. Missing/unusable date strings become null; invalid field types fail schema validation. Valid ISO instants normalize to canonical UTC milliseconds. Unknown liked dates are never fabricated from publication dates.

Availability follows only hydrated video evidence: processed public/unlisted supports `available`; explicit private/deleted/rejected supports `unavailable`; other statuses or absent evidence remain `unknown`. Playlist-item privacy is validated but does not establish video playability. Placeholder titles do not establish private/deleted status. Available is an observation, not a regional/age/universal playback guarantee.

The small duration parser accepts fixed days/hours/minutes/seconds, including seconds-only, long hours and fractional seconds, returning finite nonnegative seconds. Missing, malformed, overflowing or unsupported calendar-unit strings are null, never fabricated zero. Wrong duration field types are malformed metadata. Thumbnail preference is deterministic: uhd, qhd, maxres, standard, high, medium, default. Missing images are null. Returned known URLs require HTTPS `i.ytimg.com`, no credentials or nondefault port, and valid optional dimensions. Other hosts fail closed pending justified provider evidence. No image download/cache or CSP change is introduced.

## Errors and bounds

Provider errors have approved domain categories and safe fixed keys at phase `scanning`. Specific provider codes distinguish malformed responses, unmappable membership, token-chain failure, duplicate source IDs and incoherent counts. Request errors retain Phase 3 authentication, permission/configuration, quota/rate, service, network, interruption and unexpected categories. No raw response, exception text, token or opaque page token is logged/returned in error detail.

Network/body transport errors, HTTP 429/recognized rate-limit reasons and selected 500/502/503/504 failures get at most two additional retries per request. Daily quota, permission/configuration, schema/identity/count/token anomalies and other nontransient failures stop. Backoff is 1s then 2s plus 0–250ms jitter, with valid Retry-After honored up to 30s; longer waits stop with the rate/service error. An ingestion session shares at most six additional retries (including recovery bootstrap), one auth recovery and ten minutes of wall time including consumer pauses. Every fetch/body read has a 20-second deadline. Clock/randomness/sleep/deadline signals are injectable. Cancelled backoff/fetch/body or a clock regression cannot reach completion.

These are ingestion-session bounds. Phase 5 must compose the specification's whole-attempt budgets across its preparation/final owner checks as well as ingestion; it must not wrap this stream in an unbounded retry or reset the budget to evade caps. Provider code does not perform authorization cleanup or storage mutation; the future coordinator owns the separately specified cleanup and fencing consequences.

Documentation checks are not live API observations and do not establish an uncapped lifetime Likes library or transactional remote snapshot.

**Live provider observation remains pending as a production release-enablement prerequisite.** No real account/API request was used. The future human-controlled [live-validation checklist](release/live-provider-validation.md) observes the real bootstrap, returned Likes playlist, membership pagination, hydration and genuine terminal completion through the Phase 4 provider using the production identity. Observe naturally occurring missing/private/deleted metadata, containers, totals, tokens, thumbnail origins and completeness/cap behavior; do not manipulate the account to manufacture rare cases. Validation observation does not prune local membership unless separately authorized. Any incompatible behavior requires the specified stop/amendment process, not relaxation of the trust gate. Live evidence and explicit human approval must precede deliberate production sync/pruning enablement; the real-provider prerequisite is not claimed complete.
