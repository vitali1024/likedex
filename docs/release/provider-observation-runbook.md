## Architecture and boundaries

`wxt.validation.config.ts` explicitly builds separate entrypoints into `.output/provider-validation/chrome-mv3`. The manifest clearly labels this as RELEASE VALIDATION ONLY. It inherits the exact production key, OAuth client, scope, permissions and CSP. `npm run build` continues to produce the ordinary package without the observation page, port handler or UI. Production artifact checks reject observation markers; ESLint rejects production imports of the observation composition.

The human uses the real Options Connect and privacy agreement first. Only a button on the separate observation page can open the named validation port; the background checks the Chrome-supplied extension ID and exact page URL and permits one run at a time. A strict message accepts no owner, token, completion flag, provider-gate override or caller-selected endpoint. Disconnecting the page's port cancels the run. A port does not guarantee worker lifetime; interruption never means success, and retry is explicit from page one.

The observation service receives only existing `GoogleAuthorizationRequests.bootstrapSilently` and `createYouTubeReadSession`, plus a read-only precondition callback. It instantiates the existing Phase 4 provider. Read-only repository transactions validate connected intent, authorization deadline, storage eligibility, owner and epoch/generation fences before bootstrap, each yielded event and the final result. It blocks an active sync or owner mismatch. These reads perform no clock bookkeeping, cleanup or writes. Read failures are failures, never empty state. Ordinary production startup, Options Connect/status and independently triggered retention/authorization cleanup retain their separately authorized behavior; they are not observation writes. Close other Likedex pages during the observation to avoid confusing those operations with it.

Pages are consumed in memory, keeping only per-video aggregate classification until completion. No page reaches persistence. The genuine WeakSet-backed `TrustedProviderCompletion` is checked against this ephemeral observation scope, then discarded. It is never handed to a finalizer or returned over the port. There is no sync owner-check receipt or durable attempt. No observation result changes owner, memberships, latest success, freshness, control revision or auth deadline. Tokens remain inside the existing Chrome Identity/request boundary; neither UI nor evidence receives them. Provider errors are allowlisted categories/keys, without raw exception messages.

The output is aggregate-only: bootstrap validation, accepted page count, raw/unique/duplicate membership counts, optional reported total, hydration page count, unique lookup-returned/omitted counts, missing rich metadata, unavailable/unknown availability and genuine trusted completion. `hydrated` means a lookup entry was returned; it does not imply public/playable or complete rich metadata. `withoutRichMetadata` means title, channel name or duration is missing. Cross-page duplicate counts use the last hydration classification per video. An empty library performs no hydration. Failure can retain aggregate progress but always has `trustedCompletion: false`. The temporary view expires ten minutes after the last update, checked by timer and focus/visibility resume, and is never saved in extension storage. Copy required sanitized evidence before expiry; your human-held copy is outside extension storage.

## Verification and lifecycle

`npm run verify:provider-validation` covers deterministic real-adapter/provider behavior against synthetic Chrome/fetch boundaries and actual Dexie/fake-indexeddb. Every case compares every raw store before/after, including old unrelated membership, terminal attempts, latest success and freshness/control bookkeeping. Spies assert no page application, claim, finalizer, authorization renewal or cleanup. Genuine trusted empty is included, proving this is not merely a failure-only no-write path. Malformed bootstrap/page, partial enumeration, hydration failure/omission/private data, real provenance versus copied/missing proof, cancellation, changing fences, owner mismatch, preconditions and token sentinels are covered.

`npm run verify` also checks strict types/lint, all existing suites, production and validation builds, package boundaries and Chromium E2E. The added browser test uses a clearly separate **TEST COMPOSITION** with synthetic OAuth/fetch boundaries installed before background startup. It proves actual reserved ID, Options agreement/Connect, exact sender routing, multi-page observation, all-store equality and closed Sync. This is not live Google/YouTube evidence or independent review. High-risk independent release review remains required.

Keep this mechanism as a **development/release-only tool** while the provider gate and later provider regression checks need repeatable observation. If human review accepts a lasting tool, suggested commit is `chore: add non-destructive provider validation path`. Never package it as product functionality. It may be removed after approval if no ongoing release-validation need remains; removing it should also remove its config/scripts/tests/runbook and the dedicated read-only repository hook. No automatic commit or removal is performed.
